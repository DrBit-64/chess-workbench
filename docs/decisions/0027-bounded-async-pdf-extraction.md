# ADR 0027：有限并发的模型调用与串行本地提取处理

- 日期：2026-10-03
- 状态：已实现并完成有限范围的正式网站实测；细节见 [验收记录](../agent/pdf-concurrency-implementation-2026-10-03.md)。
- 目标：多个独立 PDF 提取任务重叠等待 DeepSeek，本地处理保持串行，复用 v8/v9 的识别、审核和发布。
- 执行顺序与验收：[实施计划](../agent/pdf-concurrency-plan-2026-10-03.md)。
- 继承：[ADR 0009](0009-sql-jobs-and-local-engine-runtime.md)、[ADR 0019](0019-sqlite-write-coordination-and-job-recovery.md)、[ADR 0026](0026-source-unit-scoped-incremental-review.md)。

## 1. 边界与现状

用户需要批量处理棋书，接受有限数量的异步请求，不需要多进程部署或通用工作流平台。本次只改变任务之间的调度；同一任务内的关系批次继续顺序执行。模型输入、阅读范围、分窗、推理与输出额度、来源归属、人工修订和批准语义保持现有行为。

当前 `SqlWorker.run_forever()` 在 `run_once()` 完整结束后才领取下一个任务；模型调用本身已使用 `httpx.AsyncClient`。`generate_relation_chunks()` 则以先前响应更新 `RelationState`，然后生成下一批输入。这条语义依赖不能用无条件 `gather()` 拆掉。

本次检查还发现：

- PDFium 在多个入口通过默认线程池调用；一旦增加活动任务，它们可能同时进入不支持多线程并发的 PDFium。
- `commit_verified_append()` 在 SQL 事务内写合并文件，需要拆成事务外准备与短事务提交。
- 当前已保存逐批请求/响应，但完整候选的自动重放不等于中途批次可以自动续跑。
- 最终工件登记不能仅依赖“任务还在 running”；要核对当前执行者和领取轮次，拒绝失去租约的旧执行者。

## 2. 三个职责

| 职责 | 保存/执行的内容 | 并发规则 |
| --- | --- | --- |
| 提取协程 | 一项任务自己的原文引用、分窗、`RelationState`、已处理响应、v9 前驱快照 | 默认 2 项活动任务，可配置到 3；每项最多一个在途模型请求 |
| 模型调用器 | HTTP 请求、超时、响应/网络错误，统一使用主生成与补问额度 | 全进程默认最多 2 个在途请求；等待时不持有本地阶段或数据库资源 |
| 本地处理通道 | 按阶段执行渲染、构造输入、解析/应用响应、编译和结果准备/提交 | 同一时间一个本地提取阶段；结束后让其他任务进入 |

网页请求、任务心跳和取消监督不排在长时间的本地处理后面。网站审核仍可进行，它与提取结果通过短事务和版本检查协调；“本地串行”不是给整个网站加一个总锁。

运行示例：本地准备 A1 → 发出 A1 → 本地准备 B1 → 发出 B1。若 B1 先返回，先保存/应用 B1 并准备 B2，A1 继续等待。不要等待整组请求全返回，也不要按提交先后阻塞已经返回的其他任务。

## 3. 技术栈与最小实现

沿用一个 Sanic 进程、Python 3.13 `asyncio`、HTTPX、SQLAlchemy/aiosqlite、SQLite WAL 和现有 SQL `jobs`。不增加 Redis、Celery、消息代理、分布式锁或持久化协程框架；也不手写 epoll。

增加一个由应用生命周期持有的小型提取运行时，包含全局 API 限制器、本地串行阶段入口和专用同步执行器，显式注入 v8/v9 服务。生产中的主生成、补问必须共用它，不能每次构造 provider 就新建一个限流器。现有 provider 测试替身仍可注入。

配置建议：

- `CHESS_WORKBENCH_PDF_WORKER_CONCURRENCY=2`：最多领取/加载多少个 PDF 任务；设为 1 可恢复单任务调度。
- `CHESS_WORKBENCH_CCEF_PROVIDER_CONCURRENCY=2`：主生成与补问合计在途数。
- 本地处理并发固定为 1；同一文档活动追加固定为 1，不新增面向用户的调参表单。

上述配置已实现，默认均为 2，可设置为 1–3；首版只针对这一小规模。Stockfish 的已有运行限制不能随着 PDF 并发数被放大。后台任务总开关保留原有兼容性。

调度器只领取还有活动名额的任务；余下任务保留在 SQL 队列，不能提前加载所有 PDF。复用现有每任务监督逻辑和条件领取，不需要把每一批都变成一条 SQL Job。若采用 TaskGroup，普通单任务失败必须在任务内部处理，不能触发其他提取任务一起取消。

### 3.1 本地阶段的粒度

将原本跨越整个提取的函数在已有外部调用边界处分段，而非改写所有领域函数：

```text
短事务加载引用 → 本地准备页证据/输入 → 退出本地阶段
→ 等待 API 名额 → 发送并等待 HTTP → 释放 API 名额
→ 本地保存响应并应用关系 → 退出本地阶段
→ 下一批，或者本地编译/保存文件 → 短事务登记正式结果
```

页渲染以一页为阶段，不用整个几十页范围长期占住本地通道；一批响应的解释/编译可以作为一段。同步耗时工作通过专用执行器离开事件循环，不能因线程外包又放开本地阶段的串行约束。所有 PDFium 对象的打开、使用和关闭统一在单个专用线程完成，包括审核取图和增量补前页的渲染入口。

本地入口可以是一个小型非重入 gate，或一个消费者的阶段队列；选择改动较少者。阶段内部禁止再次等待本地入口，也禁止发起并等待 provider。取消 `to_thread` 的 await 并不等于底层函数已经停止：仍在运行的本地阶段必须收拢后才算释放，线程返回的数据在任务已取消时不得应用。不要把这些规则扩展成通用调度 DSL。

## 4. 上下文与检查点

### 4.1 内存状态

协程暂停时已有局部变量会保留，不必序列化 Python 调用栈。每项任务独享 `RelationState.games/lines/parent/token_line/events/problems` 和当前批次，不共享可变棋树。原书文件与已落盘证据通过引用复用。

### 4.2 最小持久化

复用现有内容寻址文件存储，在每次模型调用处增加小型检查点索引；大文本不塞进 Job 行。索引可以是运行目录中的原子写文件，无需默认增加表或迁移。一个运行始终只有当前有效执行者可以登记检查点；若实现选择数据库索引，也只加当前查询/一致性需要的最小记录。

检查点包含：运行 ID、流水线/检查点格式版本、稳定批次标识、类型（关系批次或补问）、输入指纹、请求/完整响应文件引用和哈希、调用时间与用量、是否已收到完整响应。运行登记另绑定原书/证据、分窗方案，以及 v9 的文档和人工审核版本。

输入指纹覆盖完整消息与结构约束、有效模型/endpoint（不含密钥）、输出和推理参数、来源/前驱绑定。不得只用页码、批次序号或 `attempt_count` 判定可复用；重启后的同一运行、同一输入应跨执行轮次复用。不是跨所有任务的语义缓存。

恢复流程：

1. 已有完整正式候选时，沿用现有候选重放。
2. 否则加载固定证据、原始分窗和前驱快照，重建空的任务状态。
3. 顺序构造请求；找到一致的完整响应就重放，缺失时才付费调用。
4. 收到的完整响应先持久化，再应用关系；每次恢复从该运行的基线重新折叠，避免“重复应用第 k 批”。补问响应及其已接受决策也沿用同一规则。
5. 无效 JSON/输出截断等诊断原样保留，不把“有文件”当作成功；同输入已有响应不因编译失败就自动重新计费。仍走现有局部待审/补问策略。

编译器版本或分窗改变时，禁止把旧的内部状态与新的响应混用。允许在明确的同一来源/语义协议下重放保存响应做本地编译修复，但已登记的历史工件不覆盖。若更新导致后续请求不同，旧后续响应不匹配就不能复用；执行者应报告这一点而不是静默整单重跑。

未收到完整响应的在途请求存在“供应商可能已经收费”的不确定性。本地检查点只能避免重复提交已保存的结果，不能承诺外部调用 exactly-once。自动重试沿用单一有界策略，不能叠加 provider、批次、整单多层无限重试。

## 5. 资源等待与提交约束

| 场景 | 必须遵守的约束 |
| --- | --- |
| 等待 API 名额或 HTTP 响应 | 不持有本地 gate、SQL session/连接或写锁 |
| 本地阶段需要 SQL | 只在叶子函数执行短事务；任何已有 SQL 事务不得反向等待本地 gate |
| SQLite 单连接 | 不在已占连接的函数中另开 session 或嵌套调用 `run_write`；每事务独立 session |
| 同一文档追加 | 保留活动追加排斥、固定前驱/审核快照和提交版本检查；不让后继占满名额再等前驱 |
| 取消/租约丢失 | 停止发送新请求，收拢子任务；正式登记检查当前 Job、执行者、领取轮次和取消状态 |
| 已返回结果等待处理 | 先释放网络名额；不能占住该名额等待满的结果队列，而消费者又在等 API 名额 |
| 重试退避 | 不占 API、本地或 SQL 资源；不重新调用已落盘的匹配响应 |

增量合并文件在事务外准备；进入短事务后复查 document version、review revision 和执行者，再推进文档 head。版本冲突保留模型响应供处理，不能覆盖新的人工作业。`Database.run_write` 的锁与 session 的取得顺序沿用统一边界；不要为本次重构整个仓库的所有服务。

主生成与补问均有网络超时和可配置/清晰的请求总时限，总时限从实际发出请求开始计时，排队时间单独记录。总时限按现有正常调用耗时选择，不擅自缩小输出或推理额度。保活数据不能使请求无限占位。

## 6. 观测与网站行为

记录少量可核验的阶段信息即可：`run_id`、批次、执行轮次、阶段开始/结束、实际 HTTP 开始/结束、是否重放、用量和失败原因。日志不含密钥；原文只放既有本地证据/响应工件。排队、HTTP 和本地耗时分开，不能拿 Job 的 running 时间假装 API 有重叠。

继续从正式 `POST /api/pdf-extractions` / 追加接口进入正常数据库和存储。Sources 页面可以看到各运行状态，完成后各自打开 `/sources/pdf-extractions/{run_id}/review`。检查点无需新增管理后台；如需显示阶段，复用已有状态/详情位置即可。

本次为个人网站，聚焦下面实施计划中的用户可见结果和少量真实并发故障。不得恢复已退役 CI、全面 R5/P6 测试、全库多方言/组合穷举或分布式部署。
