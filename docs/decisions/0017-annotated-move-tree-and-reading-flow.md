# ADR 0017：带原子注释的棋谱树与独立阅读流

- 状态：Accepted
- 日期：2026-08-14
- 依赖：ADR 0010、0014、0015、0016

## 背景

Stage 8D 的真实五页审核发现，CCEF 1.0 虽然能分别表达 `move_sequence` 与带锚点的
`prose`，却不能无损表达棋书中最常见的一种结构：一条连续主谱在某步后被说明文字
暂时打断，文字中包含从更早局面分出的括号变化，随后原主谱继续。把每个片段重建为
从第一步开始的独立棋谱会复制公共前缀、破坏真实分叉点，也无法按原书顺序把说明放回
棋谱中。

棋局拓扑与阅读顺序是两个不同维度。例如来源先打印主线 `6.Be3`，随后用一段文字讲解
从 `5...Nc6` 后分出的 `6.O-O` 变化，再回到主线 `6...O-O-O`。变化的棋局父节点是
`5...Nc6`，但其来源显示位置位于 `6.Be3` 之后；两者不能用同一个顺序或锚点冒充。

另外，整段 prose 不适合作为棋谱旁的审核与知识单位。面向具体局面、棋步或变化的说明
应拆成原子注释，通常是一句话，但不能用句号正则机械切分姓名、缩写、回合号或棋步
标点。无局面关联的比赛背景、章节叙述等内容仍是顶层 narrative prose。

## 决定

### 1. CCEF 1.0 保持不可变，新增 1.1

已有 `chess-content-extraction/1.0` 模型、Schema、raw/normalized 工件与读取行为不静默
改变。新增版本字面量 `chess-content-extraction/1.1` 和独立 Schema ID/artifact。1.1
继承 1.0 的证据、来源、诊断、顶层 item、棋步合法化和 strict/extra-forbid 规则，只扩展
`move_sequence` 的可表达能力。新 provider 管线在后续独立步骤切换到 1.1；旧任务仍可按
1.0 读取和审核，不做原地升级。

### 2. 一个连续对局或理论线保持为一棵棋谱树

同一标题作用域内、同一起始局面且属于同一连续对局/理论线的内容保持为一个
`MoveSequenceItemV1_1`。棋步仍由 `parent_id + sibling_order` 表达：同一父局面的
`sibling_order=0` 是来源主线，更大的值是来源变化。括号变化必须挂在实际分叉局面，
不得为了局部显示复制从起点到分叉点的公共前缀。

节点数组保持父先于子的拓扑顺序。过滤阅读流中的 move 引用必须逐项等于节点数组 ID，
所以阅读流可以在节点之间插入注释，却不能隐藏、复制或重排棋步。

### 3. 序列内原子注释

CCEF 1.1 的 move sequence 增加 `annotations`。每个 `SequenceAnnotation` 具有本地唯一 ID、
原子说明文本、plain/markdown 格式、非空 evidence、置信度、warning、extensions，以及
可空的语义锚点。

语义锚点可以是：

- `move_node`：引用同一序列的节点，并声明说明针对该步之前或之后的局面；
- `position`：引用来源明确给出的六字段 FEN；
- `null`：说明属于当前棋谱阅读流，但无法可靠绑定一个棋局位置。

原子注释通常是一句完整判断或解释。模型应按语义生成原子单位；消费者不得用简单标点
规则二次切句。每条注释必须独立保留原始证据，拆分不能丢失页码、bbox、offset 或
fragment hash。

### 4. 阅读流与语义锚点分离

CCEF 1.1 的 move sequence 增加必填 `reading_flow`，由 `move` 或 `annotation` 判别引用组成。
它是序列内部的来源显示顺序，而不是棋局父子关系。过滤 move 引用必须完整且按顺序覆盖
所有节点一次；过滤 annotation 引用必须完整且按顺序覆盖所有注释一次。所有引用必须解析，
两类 ID 在序列内不得碰撞。

因此，一条注释可以在来源中显示于 `6.Be3` 之后，同时语义上锚定 `5...Nc6` 后的局面或
变化根 `6.O-O`；后续主线 `6...O-O-O` 仍以 `6.Be3` 为父节点。前端按 reading flow
插入注释，按 parent/sibling 计算主线与变化缩进。

### 5. 顶层 prose 继续承担叙述内容

章节导言、比赛背景、作者经历和不依赖具体棋局位置的说明继续使用顶层 `ProseItem`，不
强行塞进棋谱。正文中的孤立计划招法也仍是 prose，而不是 move node。只有具有可验证的
棋谱上下文和真实分叉父局面的编号变化才能进入棋谱树；无法唯一连接时保留 prose 或
unresolved，禁止猜测父节点。

### 6. 先验收 JSON，再修改审核 UI 和账本

实施顺序为：1.1 合约 → provider 提示与解码 → 通用规范化/合并 → 页 319–323 离线 pretty
JSON 审查 → read/inspection/UI 消费。真实书籍只用于本地人工验收，测试使用无版权合成
文本，生产代码不得包含书名、页码、具体棋步、预期节点数或 fragment hash 特判。

在五页 JSON 能正确表达连续主线、真实局部分支、嵌套变化、原子注释和来源证据之前，暂停
8D-4。审核 ledger 的 revision 必须保存最终认可的规范结构，不能先固化已知不足的 1.0
显示模型再立即迁移。

## 后果

- 棋谱拓扑、来源阅读顺序和说明语义各有明确职责；
- 主线可被说明暂时打断后继续，变化无需复制公共前缀；
- 其他网站可以直接消费版本化 1.1，而不依赖 ChessWorkbench SQL/UI；
- 1.0 工件继续不可变，升级通过新提取任务或显式转换产生新身份和 hash；
- provider、规范化、inspection、review API 和 UI 都需要分阶段增加 1.1 支持，不能作为一个
  跨模块大任务一次完成。
