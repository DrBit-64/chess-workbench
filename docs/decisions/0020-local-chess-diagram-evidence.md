# ADR 0020：本地棋盘图识别作为共享 PDF 证据

- 状态：Accepted
- 日期：2026-08-30
- 依赖：ADR 0013、0014、0017、0018

## 背景

残局书和部分中局书的例局并不从标准初始局面开始，而是先给出一张棋盘图，再从图示
局面继续记谱。现有 PDF 流程只把文本和 OCR 结果交给文本模型；模型看不到页面 PNG，
因此不能可靠恢复这种棋谱的初始 FEN。把残局书交给一套独立提取管线则会复制页码、
工件、增量拼接、模型修复和审核逻辑，并使普通棋谱与图示棋谱逐渐采用不同语义。

## 决定

1. 棋盘图识别是 ADR 0013 来源证据层的一个可替换本地端口，不是新的 PDF pipeline。
   PDFium 在原有确定性页面渲染之外，提取带页面坐标的普通嵌入图片候选；没有可用图片
   对象时，识别器可以在同一张已渲染页面上回退检测。
2. 默认实现先以传统图像几何寻找轴对齐的 8×8 棋盘，再用单一、可单独安装的本地 ONNX
   方格分类器识别 64 个格子。模型不接触网络、SQL、CAS 或 Job；模型文件有固定 URL、
   SHA-256 和许可证记录，并可通过 `ChessDiagramRecognizer` 端口替换。
3. 识别阶段只可信地产生棋子摆放、图片位置和置信度。运行局面解析器从棋盘之后有限范围
   内的首批正式编号着法推断行棋方与回合数，并用 `python-chess` 要求该着法从候选局面
   唯一合法。书页不能提供的王车易位、吃过路兵和半回合信息分别固定为无、无和零。
   无法唯一解析时保留图示证据并将 `operational_fen` 设为 null，禁止猜测。
4. 解析结果被编码为 `origin=diagram` 的 `SourceEvidenceFragment`，按页面纵坐标插入原有
   文本/OCR 阅读流。之后仍使用同一 `ocr_fragment`、manifest、CAS 登记、整段 prompt、
   DeepSeek provider、CCEF 规范化、增量合并、失败修复和人工审核边界。不得增加棋盘图
   专属数据库、Job kind、候选格式或第二次大模型调用。
5. Prompt 只能逐字采用本地提供的非空六字段 FEN。它应将新例局开头的图示局面作为
   `initial_position`，把既有棋谱中间的图示视为校验点；null FEN 只能成为 figure 或
   unresolved 内容。
6. 模型文件缺失、页面没有棋盘或低置信度识别均不阻断普通 PDF 提取。识别器内部错误被
   净化为页面 warning，文本证据仍继续处理。新的识别语义进入 extraction profile
   fingerprint，历史不可变工件不被覆盖。

## 后果

- 从初始局面和从图示局面开始的棋书共用一套数据与修复机制；后续替换分类器不会改变
  CCEF 或数据库契约。
- 局面解析是保守的：当图后没有可唯一验证的编号着法时，系统宁可交给人工审核，也不
  构造一个看似完整但不可信的 FEN。
- 当前检测只承诺印刷品中轴对齐、可分辨的传统棋盘图。透视照片、彩色装饰棋盘和手绘图
  可在同一端口下增加实现，不得据此分叉业务流程。
