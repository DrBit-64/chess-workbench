# 2026-09-27：人工锚点驱动的 Catalan 修复试验

## 结论与范围

**程序重放能显著省去重复录入，但本样本尚不能完整自动修复；本轮模型修复未通过。**

操作者要求先实测程序能否利用已保存的人工修正恢复后续，再在必要时实测模型辅助。
本轮新增离线试验脚本、独立来源验收数据及记录，未改产品提取/审核功能，未启动网站、未写审核数据库。
网站上的人工修订仍为 v15。没有把试验候选当作用户的新审核版本，没有接通自动修复按钮。

只使用 Catalan 最新任务 `96b116f8-ee91-563d-b78c-692ea811f7f9` 的物理 p10–17。
不针对书名、页码、颜色或某招编写产品修复特判；下述固定来源引用只属于该样本的**独立验收数据**，
不输入修复算法或模型。此试验不能代替其它书籍或 R5/P6 的验收。

## 1. 读取到了哪些人工修正

审核历史可见：

- v2：把 `10...Ba6` 从 `10.b3` 后移到 `10.Bf4` 后。
- v3–5：将三个额外样式疑点卡片改成正文；这些来源中的棋步已在树里，不能再生成重复棋步。
- v6–15：用十次片段转换新增 48 个半回合，其中 `10...a5` 分支 4 招、`10...Bb7` 长分支 41 招，
  实战 `11.b3 Rc8 12.Nc3` 3 招。

原始结果 55 招 / 70 待审，当前人工修订 103 招 / 57 待审。
这里“招”按一个白步或黑步计，即半回合。

## 2. 程序试验：只用 v2 的一次改挂

为避免“把用户后来补录的答案抄回去”，生成关系补丁时明确指定 `--human-revision 2`。
程序只读取 v2 的父节点改动，映射回原 PDF 的精确来源出现，拆开原来混在同一个 segment 中的
`10.b3` 与 `10...Ba6`，把后者接回已知主线尾部，再重放保存的模型关系。
没有重新调用模型，没有扫描所有能够合法走该招的局面。

**v6–15 的 48 招仅用于事后核对，不参与这次程序修复。**
结果全部与后来的人工录入同时满足：完整 UCI 祖先路径一致、来源片段匹配、棋步合法、唯一对应。
第一次人工改挂也保持一致。理论上这十次新增片段操作可以由一次重放预览代替。
这证明的是可恢复性和对应关系；尚未实现保留现有节点 ID、正文修改的生产合并。

| 检查项 | 原始保存结果 | v2 修正后离线重放 |
| --- | ---: | ---: |
| 合法棋步 | 55 | 141 |
| 尚未装配的关系问题 | 67 | 30 |
| 棋规失败子树局部隔离后的待审项 | 70（含 3 个样式卡片） | 31（不重建样式卡片） |
| 后来人工新增 48 招的完整路径及来源匹配 | — | 48 / 48 |
| 整局来源路径核对 | 未据此验收 | 132 / 262 |
| 来源中仍缺失的正式棋步 | — | 121 |
| 完整正确的印刷变化 | — | 13 / 30 |

重放原始候选其实有 186 个节点，其中 45 个依赖错误局面的后代不能通过棋规校验；
局部隔离后剩 141 个合法节点。即使这些节点都合法，仍有来源错误：

- 原有 `7...c6` 被之前的自动样式补问挂进 `5...Bd6` 变化；其 8 招路径均不符合原文。
- `14.Be3` 被挂在 `13...Bb4` 后，在那个局面上仍然合法；后继 `14...Nhf6` 才发生棋规错误。
- `13...Nh5` 应恢复实战主线；第 19、21 步附近还有独立的恢复主线错误。

因此不能接受“141 / 141 合法”作为整局修复成功，也不能据本试验宣称用户只需一次修改就能修完整局。

### 独立来源验收

[来源核对表](pdf-review-catalan-recovery-oracle-2026-09-27.json) 覆盖从 `1.Nf3` 到 `34.Qh5` 的
67 个实战半回合及 30 条正式印刷变化，总计 262 个不同棋步出现。
重复引述的 `13.e4` 和 `34.Qh5` 不作为新走一遍的棋步。

验收比较精确来源父节点、完整来源祖先路径、主线身份、合法性与缺谱；
其中 p10、p13、p14、p17 另对照了真实页面图像，其余使用保存的连续原文和样式。
核对表本身另经一次离线自洽校验：262 招全部合法且无关系装配问题；这是验收数据校验，**不是自动修复成果**。
正文提及的计划和注释锚点不计入这 262 招，**本轮没有验收全部注释挂载和正文排版**。

## 3. 模型辅助：实际调用了三次，均未获得可采纳修复

自动审批最初拒绝外发 p10–12；操作者明确补充授权后才启动调用。
请求仅包含此任务 p10–17 的保存文本/样式/相关结构、原有关系和 49 条人工约束，未发送整本 PDF。
试验保留完整连续语境，同时要求只输出现有来源关系补丁；没有把独立验收答案告诉模型。

| 尝试 | 模式和输出上限 | 结果 |
| --- | --- | --- |
| model1 | 高推理，24,000 | 24,000 全用于推理，没有最终内容；首试未配置原始失败响应记录器，保留请求及异常证据 |
| model2 | 低推理，16,000 | 输入 27,127 token；16,000 全用于推理，没有最终内容；保存失败响应及诊断 |
| model3 | 关闭推理，10,000 | 约 5.35 秒完成；输入 27,102 / 输出 1,552，正常结束，但补丁语义不合格 |

第三次 JSON 符合 `RelationPatchResponse` 的字段格式，却存在实质错误：

- 8 个 additions 中有 43 个来源棋步已经属于现有 segment，造成重复领取。
- 把已有正式棋步作为某段注释的 promotion，`apply_relation_patches` 拒绝：
  `relation promotion does not cite unused note moves`。
- 把 `seg_main_15` 的入口接到它自身包含的 `26.Ne5`，形成自身依赖。
- 仍将黑方 `13...Nh5` 作为白方 `13.e4` 的替代，而没有确认其主线接续身份。

这不是只差一个 JSON 字段，也不应通过删除校验或提高合法率评分来采纳。
本轮不重试、不修饰这份模型响应为成功结果；没有接受任何模型补丁。
第三次只命中 1,280 输入缓存 token，不能假设连续三次相似输入就会有大量缓存命中。

试验前后余额只读查询为 ¥18.99 → ¥18.87，观察到的差额约 ¥0.12。
完成三次后已停止新增生成请求。

## 4. 这对工作流意味着什么

本次证据支持优先交付以下程序能力：

1. **把人工修正写成来源约束。** 用户依旧点棋步；后台记录实际来源出现及其前驱，
   而不是只改变当前 CCEF 中临时节点的父 ID。
2. **用保存响应重放依赖部分。** 一个入口修好后，已有的明确关系可以继续装配。
   先预览新增、改变、冲突；同一路径与来源的既有人工棋步复用，不重复新增。
3. **把其它独立错误留成少量入口问题。** 不能把一个错误入口的全部后代都变成需要逐条补录的任务。
   与现有人工内容冲突的部分不覆盖，其余独立恢复成果保留。
4. **一次确认保存为原有可撤销审核修订。** 保留用户现有节点、人工正文与不可变历史。

本轮原型仅自动处理“已有来源棋步改挂到已知线路尾部”的情况。
任意跨线路中途改挂、已有人工内容合并、按依赖根因组织 UI 仍待产品实现；不能把它包装成通用修复功能已经完成。

### 模型部分应先缩小任务，再追加验收

此次直接要求模型维护整局现有的 segment/line/patch/promotion/addition 结构，未获得可靠结果。
它同时承担了来源理解与结构修改两类工作，发生重复节点、自依赖和语义误判。
“人工反馈有用”已有程序证据；“加上人工反馈后整局模型修复就可靠”尚无证据。

下一次更合适的试验是保持连续原文输入，但每次只输出一组独立疑点的来源判定，例如：

- `13...Nh5` 应接在哪一次来源出现之后，是否恢复已确认实战线路？
- `14.Be3` 应接 `13...Nh5` 还是 `13...Bb4`？引用哪句解释或局部版式作为依据？
- 哪个印刷前缀只是重复引述，而非新走一步？

程序再负责生成拆段/改挂操作，更新相关引用并重放依赖。
不能让模型重新添加已经存在的整批棋步，也不能为省输入退回仅给最后若干个合法节点。
这项**小范围来源判定协议尚未实现、未实测**，不能现在承诺它能修完整局或保证只需 1–3 次人工操作。
下一步应先验证一个问题组成功，再决定接入；不要默认多轮整局重提或盲目增加推理额度。

产品化开发仍按个人网站尺度：一个真实恢复预览、一条人工内容不被覆盖的关键回归，
不引入通用工作流框架、不运行全局覆盖率和全部 P6。

## 5. 工件与复现

本轮脚本：

- `scripts/replay_pdf_relations.py`：提取只读 `load_saved_run`，原重放 CLI 行为保持。
- `scripts/experiment_pdf_review_recovery.py`：从人工修订导出来源改挂、保存响应重放、人工路径核对。
- `scripts/experiment_pdf_review_model.py`：显式 `--live` 才调用模型；保存请求/响应/错误，无自动重试。
- `scripts/evaluate_pdf_review_recovery.py`：只读独立来源核对表评估候选。

所有运行工件在 `data/debug/review-recovery-20260927/`：
`program-v2/` 是仅用第一次人工改挂的试验；`program/` 是早期完整 v15 对照；
`model1/`、`model2/`、`model3/` 保留三次请求和各自结果；`model3/validation.json` 记录拒绝原因。
`model3/diagnostic-patches-only.json` 只是操作种类隔离的诊断副本，未采纳、未计为成功输出。

```sh
uv run --project backend --locked python scripts/experiment_pdf_review_recovery.py \
  96b116f8-ee91-563d-b78c-692ea811f7f9 --human-revision 2 \
  --output data/debug/review-recovery-20260927/program-v2
uv run --project backend --locked python scripts/evaluate_pdf_review_recovery.py \
  96b116f8-ee91-563d-b78c-692ea811f7f9 \
  --oracle docs/agent/pdf-review-catalan-recovery-oracle-2026-09-27.json \
  --replay data/debug/review-recovery-20260927/program-v2
```

验证：上述真实保存响应重放及来源评估完成；原 `replay_pdf_relations.py` CLI 仍复现
55 合法棋步 / 67 关系问题；四个本轮脚本的定向 Ruff 检查/格式检查通过。
未新增后端功能，不跑全局测试。最后只读确认审核版本仍为 v15。
