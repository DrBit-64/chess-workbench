# PDF 有限并发：Sol 实施顺序与验收

日期：2026-10-03。状态：**C1–C4 已实现并完成有限范围正式网站验收**；详见 [实施与实测记录](pdf-concurrency-implementation-2026-10-03.md)。本文件保留原定开发顺序和验收口径。

设计依据：[ADR 0027](../decisions/0027-bounded-async-pdf-extraction.md)。用户认可三个职责：提取协程保留独立上下文；模型调用器同时等待少量 API；本地提取阶段串行。允许后续调用 DeepSeek 验收，并要求实际结果能在日常网站查看。

## 1. 本轮范围与开发尺度

- 保留 v8/v9 的输入、分窗、父子关系、来源归属和增量人工基线。只让不同任务的网络等待重叠；不做单任务内变化群并发。
- 复用现有 SQL jobs、协程和文件工件。不要新增 Redis/Celery、通用消息平台、持久化 Python 调用栈、自动调优或分布式部署。
- 默认 2 项活动 PDF 任务、2 个全局 API 在途请求；本地阶段 1 个，同一文档追加 1 个。需实测 3 个同时在途时再将两项配置一起调到 3，无须为此重复提取已经完成的片段。
- 不改变模型、提示词和额度来掩盖调度问题。有限的单任务错误不能取消另一项任务，也不能默默转为全局串行。
- 只运行直接覆盖本次行为的检查。阶段完成后再运行所属测试；不要每改一个函数就跑全库、全方言、全量覆盖率或旧 P6。文档不要求恢复 CI。
- 真实源码/原书比较是语义验收证据。不能以“棋步都合法”“任务 succeeded”或“正文都保留了”代替来源覆盖与归属检查。

## 2. C1：收紧本地阶段与资源生命周期

目标：先在并发数 1 下交付行为不变、资源边界清楚的版本。

工作：

1. 应用持有提取运行时；区分本地阶段与等待 provider 的阶段。主生成和补问注入同一个调用额度。
2. 渲染、输入准备、响应解释和编译按现有函数边界接入串行入口；不在本地 gate 内调用/等待 provider，也不在已占 SQL 连接时进入 gate。
3. 所有 PDFium 入口统一使用专用单线程执行器，包括审核取图、增量补页。同步执行中的取消要等待执行结束再释放该阶段，不能留下并行 native 调用。
4. 增量合并文件先在 SQL 事务外准备，随后短事务复核并提交。保留人工快照和版本冲突保护；审计本次触及的嵌套 session/`run_write`。

验收：

- 使用已有保存响应重放一次 v8 和一次 v9，同一输入下棋树、来源、注释和审核问题语义不变。
- 一个受控慢渲染/本地阶段期间，网站健康读取和任务心跳可运行；渲染最大活动数为 1。
- 代码与一个聚焦行为检查证明：等待模型期间没有本地 gate 或 SQL session 被长期占用。

不要为通过此阶段调用付费模型。

## 3. C2：按已完成响应续跑

目标：已经收到并保存的付费响应，在任务中断后可以自动复用。

工作：在现有保存请求/响应的位置接入 ADR 0027 的检查点；恢复时按固定基线和分窗顺序重放，恢复关系状态后继续下一批。补问也适用。继续优先使用已有完整候选工件；不覆盖旧候选、审核修订或已发布数据。

验收只需要一个具有两批依赖和一次可选补问的确定性 provider fixture，覆盖：

- 第一批响应已保存后中断，重启后第一批不再调用 provider，第二批仍得到相同的前驱结构；结果不重复入谱。
- 同输入跨执行轮次可以复用；改变前驱审核快照或实际请求后不能错误命中。
- 完整响应保存了但尚未应用时中断，恢复后应用一次；旧执行者/已取消任务的迟到结果不能提交新 head。

可以在同一聚焦测试中覆盖相关分支，不扩展成大规模故障矩阵。网络已发出但没有完整响应的情形记录为结果未知，不能承诺供应商不收费。

## 4. C3：接通两项任务与故障隔离

目标：网站正式队列允许两项任务同时等待模型，第三项排队，本地仍串行。

工作：保留每任务租约/心跳/取消监督，为每次领取绑定执行者与轮次；增加受限活动名额、统一 provider 名额及网络请求总时限。普通错误在任务内终结/有界重试；重试退避不占网络/本地资源。Stockfish 并发不跟随 PDF 配置扩大。直接从现有路由进入，不新增实验提取入口。

验收以可控制返回顺序的 HTTP/provider fixture 完成：

| 检查 | 要观察到的行为 |
| --- | --- |
| A、B、C 三个任务 | A/B 的真实 provider-await 区间重叠；C 未获活动名额时保持 queued，不提前加载整份上下文 |
| 让 B 先返回 | B 能继续自己的下一批，不被 A 的慢响应阻塞；A/B 的游戏与来源不串线 |
| 本地阶段 | 最大活动数为 1；主生成与补问合计请求数不超过设置值 |
| 取消一个慢请求 | 被取消者不再提交候选；另一项完成，释放名额后 C 可推进 |
| 模拟一次超时/429 | 不吞掉其他任务、不无限重试、不用全量任务重跑代替失败批次恢复 |
| v9/人工审核 | 同一文档双追加仍被排斥；不同文档可并行；等待模型期间人工修改可保存，旧快照提交被明确拒绝 |
| 关闭/恢复 | 所有监督子任务被收拢；未完成 Job 保持可恢复；已保存响应不会再次付费 |

复用 `test_stage6_jobs.py` 和相应提取测试，新增用例覆盖新增风险即可。测试中不调用真实外部 API，不故意杀掉用户正在运行的正式任务。

## 5. C4：Endgame 正式网站实测

### 5.1 已由 Agent 独立准备的样本

书籍：Mikhail Shereshevsky, *Endgame Strategy*, New In Chess 2022，当前 PDF 共 678 物理页。**以下均为从 1 开始的物理 PDF 页码，不使用书内目录的页码。**

| 窗口 | 页段 | 完整例局 | 原书主线对照 |
| --- | --- | --- | --- |
| A | 66–68 | Game 23 Shereshevsky–Beliavsky；Game 24 Alekhine–Sämisch | 20.Bd4!? → 38.Na6，37 半回合；34.Qd4 → 45.Bxh7，23 半回合 |
| B | 174–176 | Game 59 Topalov–Beliavsky；Game 60 Nabaty–Smirin | 72.Kb6! → 73.Ka7!，3 半回合；66.h6? → 76...Qe4+，22 半回合 |
| C | 234–235 | Game 80 Ding–Anand；Game 81 Giri–Anand | 31...Nc4 → 33.Rg3，4 半回合；52.Rb7? → 52...Rg5!，2 半回合 |

共 6 局、91 个已印出的主线半回合。这里“完整”指书中这一例局完整印出的局面、棋步和讲解；不补造从初始局面到图示起点的历史招法，也不补造作者没有印出的比赛后续。

三个末页分别出现 Game 25、61、82 的标题，尚未给出该局起始图和棋步；它们不是本次第三局应提取的棋谱。A/B/C 的开头只有上一段结语，没有上一局继续印出的招法。B 的 Game 60 标题在 p174、棋盘在 p175、结尾在 p176，是正常的跨页输入。

本轮已经直接读取原文、视觉辨认六个起始棋盘，并以 python-chess 验证所有主线及选定支线。参考文件：[pdf-concurrency-endgame-2026-10-03.json](../evaluation/pdf-concurrency-endgame-2026-10-03.json)，含六个 FEN、主线、六条关键支线和两个单步提及。只声称覆盖这些参考，不声称穷尽所有嵌套变化和注释。

特别核对：Game 60 的推荐 `66.g5!` 和 Game 81 的推荐 `52.Rb8+` 都在实战主线之前印出；不能把推荐线误升成实战主线。Game 60 的两次主线升变，以及 `68...e1=Q??` 的支线归属应分别核对。Game 80 从黑方第 31 步起局。

### 5.2 未提取核对与授权

2026-10-03 已只读核对：

- 日常网站该 PDF 的所有 ExtractionRun/Job，包括失败、取消和归档任务；历史范围并集为 p19–48、p100–103。
- `data/debug` 中有提取表的实验 SQLite 数据库。
- 已知 Endgame P6/来源提取清单和报告；相关旧窗为 p19–22、p23–27、p100–103。

在上述记录中没有 A/B/C 的重叠提取。运行前再按 PDF 内容哈希复查，防止用户在等待实现期间已经处理这些页。不能仅检查未归档成功任务，也不能为了隐藏重复给请求换一个随机 idempotency key。

用户已授权本任务选择 Endgame 新片段并调用 DeepSeek。授权执行范围按 A/B/C 选定页及必要版面/棋盘证据开展，不发送整本书。若工具审批实际拒绝，则按明确拒绝理由处理；不预先增加一次例行授权询问。

付费初轮仅三个新提取任务，实际 HTTP 次数取决于原有分窗与必要补问，并不等于固定三次。先本地预检预计批次数，沿用此前实测不超过 ¥13 的支出上限作为保守边界，启动前查看当前余额，不把历史余额当作现值。不得为了测速对相同页再跑一遍付费串行基线，不预热缓存。只有明确的真实错误需要重新判断来源时才额外调用；已保存响应能重放解决的就重放。

### 5.3 正式入口与用户可见结果

通过正常网站操作或其同一个 HTTP API，在**日常数据库与 source storage**中发起三项 v8 请求：

```text
POST /api/pdf-extractions
{ pdf_asset_id: 从网站查到的 Endgame 资产 ID,
  first_page: 66, last_page: 68, profile: {}, pipeline: "source_first" }
```

B/C 改对应页段即可，实际发送合法 JSON；使用稳定的一次性任务键并记下每个返回的 run/job ID。首轮配置 2，紧接着提交 A/B/C，验证 A/B 并发、C 排队后被推进。不要自动把三个不连续片段合并成一个增量文档。

请求和响应保存到现有运行工件；在本地验收记录中登记对应网站链接：`/sources/pdf-extractions/{run_id}/review`。这些结果必须能在用户日常 Sources 页面发现、点击打开、回看原 PDF 并播放棋步。只有临时数据库、命令行 JSON 或截屏不算完成这项要求。普通独立提取可直接打开 run review，不必为验收额外 adopt 成文档。

独立答案只用于比较，不作为额外 FEN、人工棋步或隐藏提示塞给模型。先保存未经人工修改的结果及评分，再按原书修复必要的少数局部错误；分别报告初始结果和修复后结果。允许 Agent 模拟人工修订，但不能通过改数据库或注入答案宣称识别正确。候选留在审核中供用户查看，不自动批准或发布课程。

### 5.4 实测通过标准

1. **实际发生并发**：保存 HTTP 发出/结束时间，至少两个任务的模型请求有真实重叠；最大在途数不超 2，本地阶段最大活动数为 1。报告排队、API、本地处理和总墙钟时间。重叠秒数可以作为收益证据，不伪称已做同条件付费串行对照，不硬承诺两倍加速。
2. **完整主线**：六局都有独立正确的图示起点、走棋方和打印回合号；91 个主线半回合从各自起点连续匹配，不能因来源重印而重复走一步，也不能跨游戏/任务挂接。计数一致不能代替实际路径比对。
3. **支线质量**：逐条报告参考中的六条线路是否完整、父节点是否正确；两个单步提及单列，可保留为引用，不强行算漏谱。每窗口至多 1–3 处明确可见、可少量修复的局部支线/注释问题符合用户既有容忍度；大段缺谱、起点错、整条主线错挂或串局不能据此豁免。完整记录原始问题，不要求为了零误差反复付费。
4. **网站可验收**：三个任务在 Sources 中可见，审核页面正常加载原页、棋盘和两个可播放例局；任务间信息不串线。随时回看已有任务不被另一个慢模型请求卡死。
5. **保留旧效果**：用已有 Catalan、Makogonov 的保存响应及一个 v9 已审前驱做离线重放，检查棋树/来源/人工节点不变。只因本次并发改造不重付费提取旧样本，也不展开旧六书大评估。

若图示识别本身失败，先报告这属于原有识别质量还是调度引入的问题。不能只批量排除起始图或注释，把仍缺失的主线判为通过。也不要为通过此并发任务另建一套残局识别架构。

| 位置 | 拟改动 |
| --- | --- |
| `backend/src/chess_workbench/api/app.py`、`config.py`、`.env.example` | 应用共享运行时、有限 PDF 活动名额、启动/关闭与配置 |
| `services/worker.py`、`services/jobs.py` | 保留单任务监督；领取并发、执行者/轮次传递及取消隔离 |

| `services/pdf_source_extraction.py`、`services/pdf_extraction.py`、`services/pdf_incremental_extraction.py` | 运行时/检查点注入、响应保存与恢复、执行者提交检查 |
| `services/pdf_documents.py` | 合并文件事务外准备，版本/人工快照复核和短事务提交 |
| `extraction/deepseek.py` | 统一在途名额、总时限、调用计时；也可由薄包装实现，保留 HTTPX 测试接缝 |

| 前端 Sources/审核页 | 优先验证现有列表与链接；只有状态显示确实不足时做小幅补充 |
